## Root cause of the intermittent abort (the real win)
The abort (`realloc(): invalid next size`, `corrupted double-linked list`, exit
134/139) was NOT a teardown bug and NOT caused by my changes. Proven by building
HEAD's `src/window.cpp/h` + `src/main.cpp` untouched: 8/8 aborts under
`xvfb-run -a node test/test_flags_optimization.js`. It needs a real X display.

Cause: every `BrowserWindow` runs its own GTK main loop on a dedicated
`std::thread`, so `gtk_init()`/`webkit_web_view_new()` execute **concurrently**
on multiple threads against a shared GMainContext; libX11 is not thread-safe.

Fix:
1. `XInitThreads()` once in `src/main.cpp` `Init()` (before first window). Needed
   `-lX11` in `binding.gyp` linux `libraries`.
2. Global `g_engine_init_mutex` in `src/window.cpp`, locked across
   `webview::webview wv(...)` ctor → `wv.init(...)`, unlocked just before
   `wv.run()` (so the run loop isn't serialised).
3. Existing `ShutdownWindows()` + `AddCleanupHook` still terminate/join threads.

Result: 1-window was always 10/10 clean; 2-window went from ~50% abort to 12/12
clean. Full `xvfb-run -a npm test` exits 0 three times in a row, both engines.
Note: `XInitThreads()` alone only reduced the rate (~3/10 clean) — the mutex was
the decisive fix.

## RESOLVED: the *real* exit-139 root cause (this session)
Earlier entries blamed the X11/GTK threading and "fixed" it with XInitThreads +
mutex, but the abort kept coming back (flags 7/40). The actual root cause:

**`env.AddCleanupHook(...)` (N-API `napi_add_env_cleanup_hook`) does NOT run when
the process ends via `process.exit()`** — and every test calls `process.exit(0)`.
Verified with a raw `napi_add_env_cleanup_hook` that wrote a file: it never fired
under `process.exit()`, though `Init()` did. So `ShutdownWindows()` — and every
teardown strategy layered on it (zombie deferral, `DrainEngine`, sleep, leak) —
was a **no-op**. The WebKit/JSC teardown therefore raced node's own exit and
segfaulted/aborted.

Fix (this session):
1. Export a native `shutdown()` (`Adrenaline::ShutdownCallback` → `ShutdownWindows`).
2. In `index.js`, install `process.on('exit', () => native.shutdown())`. Node's
   'exit' hook DOES run at `process.exit()` and blocks until the callback returns.
3. `ShutdownWindows()`: `RunOnEngine(DrainEngine(500))`, then signal+join the
   engine thread. Windows still open are NOT destroyed — tearing a webview down
   at exit aborts 100% of the time even after draining; the OS reclaims it.
4. `close()` parks the closed WindowInstance in `closed_windows()` (leak-on-close).
   Destroying a webview in `close()` aborts at exit for test.js/test_loadfile.js
   (which close a loaded window) — also 100%. Parking is the only stable choice.

Result: flags 0/80, delay0 0/80, many(40 open/close) 0/20, full suite 0/8..0/10.
Previously flags 7-12/40, suite ~3/20.

Diagnostic method that cracked it: write to a file from inside the hook (stderr
is not flushed by the fatal path), and time the process — a 2500 ms requested
sleep that took 0.16 s wall proved the hook never ran.

## CI breakage after merge: ubuntu-latest migrated 24.04 -> 26.04
PR #17 CI passed on `ubuntu-24.04`; the merge commit's CI ran on
`ubuntu-26.04` and failed at `npm install` with `fatal error: glib.h: No such
file or directory` (from gdk/gdkconfig.h). Root cause: the GitHub-hosted
`ubuntu-latest` image was silently migrated to 26.04 between the two runs.
On Ubuntu >= 26.04 `libglib2.0-dev` is a *metapackage* (88 KB, no headers/pc);
the GLib headers + `glib-2.0.pc` move to `libgio-2.0-dev`. So the transitive
glib include path that pkg-config used to emit for `gtk+-3.0` is no longer
guaranteed.
Note: a stock `ubuntu:26.04` Docker image with the same apt packages WORKS
(pkg-config 2.5.1 emits `-I/usr/include/glib-2.0`), so the failure is specific
to the GitHub 26.04 runner image, not 26.04 generally.
Fix: pin `runs-on: ubuntu-24.04` in ci.yml + publish.yml and install
`libglib2.0-dev` explicitly (do NOT add `libgio-2.0-dev` — it does not exist on
24.04 and would break the pinned build). Verified end-to-end in a real
`ubuntu:24.04` container: build OK, all 9 test suites pass.
